# Deployment & Operations

How PrepSuccess goes from a merged pull request to students, on free tiers only
(PRD-04 §3.3). Two environments, each with its own database:

| | Staging | Production |
|---|---|---|
| Deploys from | `main`, after CI passes | `production` branch only |
| Backend | Render `prepsuccess-api-staging` | Render `prepsuccess-api` |
| Frontend | Vercel preview deployment of `main` | Vercel production deployment |
| Database | Supabase project `prepsuccess-staging` | Supabase project `prepsuccess` |
| Swagger UI | On (`/docs`) | Off |

**Going live is a deliberate act:** open a PR from `main` into `production`,
get it reviewed, merge. Nothing reaches production on an ordinary merge.

---

## 1. One-time setup

### 1.1 Databases (Supabase)
1. Create two Supabase projects: `prepsuccess-staging` and `prepsuccess`.
2. For each, copy from **Project Settings → Database → Connection string**:
   - the **pooled** string (port `6543`) → `DATABASE_URL`
   - the **direct/session** string (port `5432`) → `DIRECT_URL`
3. Nothing else: migrations create the tables, and every table enables Row Level
   Security with no policies, so Supabase's auto-generated REST API stays closed.

### 1.2 Backend (Render)
1. In Render: **New → Blueprint**, pick this repository. Render reads
   [`render.yaml`](../render.yaml) and creates both services.
2. Create the `production` branch once: `git push origin main:production`.
3. Fill in each service's secrets (marked `sync: false` in `render.yaml`) in the
   Render dashboard. JWT secrets are generated by Render.

   | Variable | Value |
   |---|---|
   | `DATABASE_URL`, `DIRECT_URL` | that environment's Supabase strings |
   | `API_PUBLIC_URL` | the service's own URL, e.g. `https://prepsuccess-api-staging.onrender.com` |
   | `FRONTEND_URL` | the matching Vercel URL |
   | `CORS_ORIGINS` | the matching Vercel URL (comma-separate several; never `*`) |
   | `GOOGLE_CLIENT_ID` / `_SECRET` | Google Cloud OAuth client; add `${API_PUBLIC_URL}/api/v1/auth/google/callback` as a redirect URI |
   | `SMTP_USER` / `SMTP_PASS` | Gmail address + App Password (required in production) |
   | `GEMINI_API_KEY` | from Google AI Studio |
   | `SENTRY_DSN` | Sentry Node project DSN (optional but recommended) |

4. **Seed** each database once (and again after editing a catalogue), from your
   machine with that environment's URLs in `backend/.env`:
   ```bash
   cd backend && npm run db:deploy && npm run db:seed
   ```
5. **First admin:** sign up on the site, then run
   `npm run admin:promote -- you@example.com` against that environment's
   database. After that, admins change roles from **Admin → Users**.

**How a deploy runs:** `npm ci --include=dev && npm run db:generate && npm run build`,
then `npm run db:deploy && npm start`. Migrations run before the server starts;
if one fails, the new instance never becomes healthy (`/health/ready`) and Render
keeps the previous deploy serving. CI also applies every migration to a fresh
Postgres on each PR (`backend-ci.yml → migrations`), so a broken migration
normally fails long before a deploy.

> **Free plan notes.** Free Render instances sleep after 15 minutes idle and
> take ~30–50 s to wake. Free instance hours (750/month) are shared by both
> services. Render's pre-deploy command is a paid feature, which is why
> migrations run in the start command.

### 1.3 Frontend (Vercel)
1. Import the repository in Vercel with **Root Directory** `frontend`.
2. **Settings → Git → Production Branch:** `production`. Pushes to `main` then
   become preview deployments (staging); give `main` a stable alias, e.g.
   `prepsuccess-staging.vercel.app`, under **Settings → Domains**.
3. Environment variables (set per environment — Preview vs Production):

   | Variable | Value |
   |---|---|
   | `NEXT_PUBLIC_API_BASE_URL` | the matching Render URL |
   | `NEXT_PUBLIC_SENTRY_DSN` | Sentry Next.js project DSN (optional) |
   | `NEXT_PUBLIC_SENTRY_ENVIRONMENT` | `staging` / `production` |
   | `NEXT_PUBLIC_POSTHOG_KEY` / `_HOST` | PostHog project (optional) |

   `NEXT_PUBLIC_*` values are baked in at build time — redeploy after changing them.
4. **Custom domain + HTTPS:** add the domain under **Settings → Domains**; Vercel
   issues the certificate. Put the backend on a subdomain (e.g. `api.`) via
   Render → Settings → Custom Domains, then update `CORS_ORIGINS`,
   `FRONTEND_URL`, `API_PUBLIC_URL` and the Google redirect URI.

## 2. Monitoring

| What | How |
|---|---|
| Backend errors | Sentry (`SENTRY_DSN`). Only unexpected errors (HTTP 500) are sent, tagged with the request ID — search Render logs for the same `request_id`. Check a new environment with `npm run sentry:test`. |
| Frontend errors | Sentry (`NEXT_PUBLIC_SENTRY_DSN`), browser and server render errors, plus `app/global-error.tsx`. |
| Alerts | In Sentry: **Alerts → Create alert → "A new issue is created"** and an error-rate spike rule, sent to email (or Slack). An error nobody is alerted about doesn't count as monitored. |
| Uptime | `.github/workflows/uptime.yml` pings `/health/ready` (API + database) hourly. Set repository variables `STAGING_API_URL` and `PRODUCTION_API_URL`. A failure emails repo watchers. For minute-level alerts add a free external monitor (UptimeRobot / Better Stack) on the production URL. |
| Product analytics | PostHog (optional). Events: `signup_completed`, `onboarding_completed`, `skill_check_completed`, `dashboard_viewed`, `task_submitted`, `password_reset_completed`. No autocapture, no recordings, no cookies, no personal data. |
| AI usage | Admin → Analytics shows requests, failure rate and tokens (from `ai_usage`). |

## 3. Routine operations

| Task | How |
|---|---|
| Release to production | PR `main → production`, review, merge. |
| Roll back | Render → service → **Events** → redeploy the previous deploy; Vercel → **Deployments** → promote the previous one. A migration isn't rolled back automatically — write a new forward migration. |
| Change the schema | Edit `prisma/schema.prisma`, run `npm run db:migrate` against a local/dev database, commit the generated migration **with an `ENABLE ROW LEVEL SECURITY` line for any new table**. Never edit tables in the Supabase dashboard. |
| Edit skills / resources / tasks | Admin → Skills & content, or edit the catalogue files and re-run `npm run db:seed`. |
| Turn on AI trial enforcement | Set `AI_TRIAL_ENFORCED=true` (and adjust `AI_TRIAL_DAYS`) on the backend service. |
| Rotate JWT secrets | Change them in Render; everyone is signed out. |
| Deactivate an account | Admin → Users → Deactivate. The user is signed out; their current access token lapses within 30 minutes. |
